# Kitty 电子宠物 · 功能设计

> 状态：草案。本文只描述设计与范围，不含实现。
> 目标板卡：Spotpear ESP32-S3-0.85-AI（本 fork 已有支持）
> 产品方向：**A 陪伴 + B Agent 的身体 + C 养成 + D 夜间陪伴**（一个产品，四条线）

## 1. 定位

一台离线自足的桌面电子宠物：0.85 寸屏上的 Kitty，会困、会饿、会自己找你，
不依赖任何云端服务，不需要账号与激活。

插上电脑时，她把控制权交给本地 agent（例如 WorkBuddy），成为那个 agent 的"身体"。

而她的身体是**有代价的**：agent 干活消耗她的精力与耐心，你必须亲自照顾她才能让她撑下去。
这条把"挂件"和"养成"咬在一起——她不是显示器，是一只需要经营的动物。

一句话：**拔网线、断云端、公司跑路，她照样活着；而她的状态，是你和 agent 共同经营出来的；
到了晚上，她安静下来陪你睡觉。**

### 四条线为什么能并存

| 线 | 本质 | 与其他线的关系 |
| --- | --- | --- |
| A 陪伴 | 底座人格与表现层 | 没它 B/C/D 都是空壳 |
| B Agent 的身体 | 一条传输通道 | 纯管道，不占玩法 |
| C 养成 | 叠在 A 上的数值与成长 | 靠 A 的表情与 D 的作息表达 |
| D 夜间 | A 的一个时段模式 | **不是独立产品**，是 A 的行为子集 |

唯一风险是范围最大、工期最长；对策见 §14 的排期顺序，每个阶段结束设备都可长期使用。

## 2. 目标与非目标

### 目标

- 离线完整可玩：无网络、无账号、无激活流程
- 插电脑后可由本地 agent 控制：表情、说话、读状态、接收输入事件
- 养成闭环：饥饿 / 精力 / 清洁 / 亲密度四条数值，随时间衰减，需要人照顾
- agent 与养成的双向影响：agent 消耗她的状态，她的状态反作用于 agent 的行为
- 夜间陪伴：到点安静下来，微光 + 呼吸节律 + 白噪音，早上轻声唤醒
- 状态连续：模式切换不丢存档
- 在 128×128 屏、一颗灯、两个键的硬约束下把表达做满

### 非目标（明确不做）

- 云端 LLM 对话、语音助手、语音识别转文字
- 小智云协议、设备激活、云端 OTA、云端资产下发
- 触摸交互、摄像头、多机联网对战
- 手机 App

## 3. 硬件基线

| 项 | 规格 |
| --- | --- |
| SoC | ESP32-S3R8，8MB PSRAM |
| 屏幕 | GC9107，128×128 SPI（旋转由帧数据在主机侧完成） |
| 音频 | ES8311 codec + NS4150B 功放，单麦单喇叭，16 kHz |
| 灯光 | 1× WS2812B（GP13） |
| 按键 | BOOT（GP0）可用；POWER（GP2）是**电源锁存开关**，不归固件管 |
| 传感器 | **无 IMU**（不能摇晃）；**无触摸** |
| 引脚 | 见 `main/boards/spotpear/sp-esp32-s3-0.85-ai/config.h` |

未决：见 §13。

## 4. 三种身份

设备始终处于以下三态之一，切换有明确条件，且**状态向量跨模式连续**。

| 模式 | 进入条件 | 退出条件 | 行为 |
| --- | --- | --- | --- |
| `autonomous` | 上电默认；或 agent 断连超时 | 检测到 USB 供电 / 配网触发 | 完全自主：表情、行为调度、按键互动、数值衰减 |
| `docked` | 检测到 USB 供电且未握手 | 拔线；或 host 握手成功 | 插电态：睡觉、打呼；数值仍衰减但减缓 |
| `remote` | host 完成 `pet.hello` 握手 | 拔线；或心跳超时 3 s | 表现层移交 agent；行为调度器降级为"待命"；数值照常衰减 |

**关键决定：插电不等于交权。** 插上 USB 只进入 `docked`；只有 host 主动握手才进入 `remote`。
否则插个充电宝，宠物就被强行接管了。

## 5. 分层架构

```
main/pet/
  pet_core.cc       状态向量、衰减、成长阶段、存档（NVS）
  behavior.cc       行为调度器：tick、按权重挑动作
  expression.cc     状态 → 表情行 / 音效 / 灯色 / 小动作
  action.cc         动作原语执行器：唯一允许直接碰硬件的层
  agent_link.cc     USB CDC 行式 JSON-RPC，暴露 pet.*
main/gateway/       SoftAP 配网页（短生命周期，写完参数即关射频）
main/boards/       只做接线与初始化，不含业务逻辑
```

**边界规则**：`boards/` 目录下不出现业务逻辑。历史上 `feba432` 把 456 行的 GLM 客户端塞进
`boards/spotpear/...`，绕开了协议层与配置层，导致该能力既无法复用也无法关闭——本次设计不重复。

## 6. 养成数值

四条数值，0–100，随 tick 衰减，定期落盘 NVS。

| 数值 | 衰减诱因 | 补充方式 | 影响 |
| --- | --- | --- | --- |
| `hunger`（饱食） | 时间；agent 高强度工作 | 喂食 | 低了表情发蔫、动作变慢 |
| `energy`（精力） | 清醒时长；**agent 每完成一次任务扣** | 睡觉、插着 USB | 掉到 **20** 就自己睡，睡到 85 醒；见底拒绝 pet.* |
| `clean`（清洁） | 时间 | 清洁动作 | 低了掉毛、灯色发暗 |
| `affection`（亲密度） | 长期不理；被忽视的 pet.poke | 抚摸、陪玩、完成任务 | 决定主动行为频率与成长 |

### 成长阶段

由 `affection` 与总互动次数决定，共 3 阶段。**解锁的是行为意图，不是新的表情帧**：
幼体只有张望与打瞌睡 → 成长加入伸懒腰 → 成熟再加入突然雀跃。

表情素材仍是同一套 57 帧；要加新表情行意味着重做帧数据并重算 Flash 预算（§13）。

**不做"养死"**。长时间不管，她只会进入"闹脾气"状态——变冷淡、不回应用、数值停在上限以下，
但一次认真照顾就能拉回来。理由是：一台坏掉的桌面设备没有意义，情绪上的疏远比数值死亡更有力。

### 与 agent 的咬合

| 事件 | 效果 |
| --- | --- |
| agent 完成任务 | `energy -= 5`，`affection += 2`，播放"完成"表情 |
| agent 报错 / 被打断 | `energy -= 8`，播放"炸毛"表情，`affection -= 1` |
| agent 长时间思考 | 转眼睛、抓耳，`energy` 缓慢下降 |
| `energy` 掉到 20 | 强制 `pet.sleep`（她爱睡：还没见底就睡），并在 `pet.status` 里报告"累了"给 host |

这是本设计的核心：**agent 的能力受她的体力约束**，而不是她去蹭 agent 的算力。

## 7. 动作原语

固件只暴露有限的动词，离线调度器与远程 agent **共用同一套**。两套大脑、一套身体。

| 原语 | 参数 | 离线来源 | 在线用途 |
| --- | --- | --- | --- |
| `pet.face` | `emotion`, `intensity` | 情绪状态映射 | agent 指定 |
| `pet.say` | `pcm` 流（`clip_id` 未实现） | 内置合成音由设备自己挑 | 播放 host 推来的 PCM |
| `pet.look` | `dx`, `dy` | 眼球/头部偏移 | 同左 |
| `pet.attention` | `on` | 抬头看用户 | 同左 |
| `pet.feed` / `pet.clean` / `pet.play` | — | 双击喂食；清洁/陪玩只有 agent 入口 | agent 也可代劳（省事但有上限） |
| `pet.status` | — | 返回全部数值、模式、以及灯当前输出的 `led{r,g,b,level}` | 同左 |
| `pet.poke` | 事件 | 按键/唤醒词触发 | 上报给 host |
| `pet.sleep` / `pet.wake` | — | 精力见底 / 靠触摸 | agent 强制 |
| `pet.night` | `on` | 作息时段或菜单 | agent 强制进入/退出夜间 |
| `pet.task` | `ok` | — | agent 上报任务结果，换算成数值变化 |
| `pet.time` | `epoch`, `tz_offset` | 配网页手动对时 | host 对时（更准，优先） |
| `pet.volume` | `0–100` | 菜单 / 配网页 | host 调音量 |
| `pet.config` | `on` | 长按 BOOT（菜单尚未接入） | 让 host 打开/关闭配网热点；串口被占用时这是唯一办法 |
| `pet.mic_stats` | — | — | 读麦克风电平与识别统计，调试用 |

另有调试能力：`pet.say` 带 `test: true` 时把音频直接喂给命令模型而不播放，
用于在没有人工的条件下闭环验证唤醒链路。

当前实现共 17 个方法（含 `pet.hello`、`pet.ping`）。新增玩法优先组合既有原语；
需要新原语时，先问"离线时它该做什么"——答不上来说明这个原语把玩法绑死在 agent 上了。

## 8. 输入手势

**只有一个可用按键。** 板子上第二颗 POWER 键实测是电源锁存开关：按一下断电、再按一下上电，
固件读不到它（真机确认，2026-11-06）。所以全部交互压在 BOOT 一颗键上。

| 手势 | 动作 | 备注 |
| --- | --- | --- |
| 单击 | 摸摸头（`affection` +2），**四种反应随机挑一种** | 主交互；喵+挥手 / 雀跃+跳 / 咕噜+端详 / 只是看着你 |
| 双击 | 喂食（`hunger` +25）+ 咀嚼声 | 有饱食上限，撑不坏 |
| 长按 3 s | 开 / 关配网热点 | 屏幕上出现热点名与密码 |
| 配网中单击 | 关闭热点，屏幕文字消失 | 控制操作，不计亲密度 |

### 为什么没有三击

试过 `Button::OnMultipleClick(cb, 3)`，在这块板子上**不可靠**：实测连按三下会被底层库判成
`单击 + 单击 + 双击`，三击回调从不触发（串口日志实证：`Petted / Petted / Fed: hunger 100`）。
一个一半概率不生效的手势，比没有更糟，所以去掉；`clean` / `play` 只保留 agent 入口。

### 为什么没有长按菜单

早期想用长按进极简菜单（配网 / 夜间 / 静音 / 音量三档 / 退出）。评估后放弃，理由见 §15：
四个选项都有更短的替代路径，而菜单要在 128×128 上画界面、做单击切换/长按确认/超时的状态机。

### 误触与降级

单键多义必然误判，规则是**宁可少做，不要做错**：

| 情况 | 处理 |
| --- | --- |
| 双击窗口内只按了一下 | 退化成单击（摸摸头） |
| 长按没到 3 s | 退化成单击 |
| 配网中误点一下 | 热点关掉，重新长按就是 |

喂食有上限，最坏结果是浪费一次动作，不会把她撑坏。

## 9. 与 agent 的协议

- **传输**：USB CDC 串口，一行一条 JSON（MCP stdio 风格的 JSON-RPC 2.0）
- **握手**：host 发 `pet.hello` → 设备回 `status` + 固件版本 + 能力表。未握手不进入 `remote`
- **心跳**：host 每 1 s 发 `pet.ping`；3 s 无输入即回 `autonomous`
- **事件**：设备主动上报，无 `id`：`pet.poke`、`pet.called`、`pet.state_changed`、`pet.tired`

```json
{"jsonrpc":"2.0","id":7,"method":"pet.face","params":{"emotion":"happy","intensity":0.8}}
{"jsonrpc":"2.0","method":"pet.poke","params":{"source":"button","count":3}}
{"jsonrpc":"2.0","method":"pet.state_changed","params":{"energy":12,"hunger":40,"mood":"tired"}}
```

选择串口而非局域网的理由：USB 供电与数据同一条线，插上即有；不引入 WiFi 常开的功耗。
若将来需要无线控制，再在 `agent_link` 增加一条 WebSocket transport，动作原语与协议不变。

## 10. 离线玩法

### 行为调度

1 s tick 更新衰减；每 18 s 左右（按性格缩放）按权重表挑一个候选动作。
当前权重表：发呆 30 / 张望 25 / 伸懒腰 12 / 哈欠 10 / 跳 6 / **打瞌睡 50** —— 她是个爱睡的猫，
待机大半时间在打瞌睡。权重由数值与成长阶段调制：累了哈欠瞌睡更多、开心或亲密高更爱跳、
冷淡更爱张望。

**不使用 LLM**。离线"智能"来自状态衰减 + 权重随机，成本为零、确定性可测。

### 表达

- 表情：沿用现有 57 帧 / 9 行动画，按情绪选行，按数值选强度
  （注意：素材的九行是**动作**，不是九张脸 —— 见 §16 的实现记录）
- 音效：见下面「声音」一节。合成短音，不做 TTS
- LED：WS2812 表达情绪，替代目前的"设备状态灯"。**颜色 = 情绪，节奏 = 状态**，
  两者独立组合：3 s 呼吸（正常）/ 6 s 深呼吸（困、累、冷淡）/ 双闪（饿）/
  4 Hz 快闪（被接管）/ 常亮（睡着，余烬色）；事件闪（叫名字白、任务完成绿、
  失败红）短暂盖过情绪色后自动回到呼吸。颜色表在 `pet_expression.cc`，
  节奏在 `pet_action.cc` 的 `LedPattern`。
  灯**默认关闭**：桌上的一颗高亮 LED 默认亮着只会碍事（接管时的 4 Hz 快闪尤其如此），
  要用户在配网页显式打开。旧固件把 100 写进了 NVS，升级时有一次性的迁移把它清零
  （`led_rev` 标记）。
  配色的硬要求：**必须饱和**。最早一版用 `(255,208,160)` 做平静色，满亮度就是一颗
  白灯，情绪全被抹平了；现在平静是暖橙 `(255,140,40)`，其余同法。

### 声音

她的嗓子只有两件事：**表达情绪**、**被 agent 拿去说话**。没有语音识别，也不做 TTS。

**六种合成音**（`pet_audio.cc`，全部现场生成，零 Flash）：

| 声音 | 听起来 | 触发 | 合成 |
| --- | --- | --- | --- |
| `kMeow` 喵 | 短促的"喵呜" | 摸头、被叫名字 | 470 Hz 起，正弦滑到 800 Hz 再落回，叠 7 Hz 颤音，350 ms |
| `kHappy` 雀跃 | 两声上扬的"啾啾" | 开心、被唤醒、agent 陪玩 | 900 Hz 0.06 s + 1250 Hz 0.07 s，中间留 60 ms 空隙 |
| `kYawn` 哈欠 | 拖长的"哈——" | 困、精力低 | 330 → 200 Hz 下滑 + 12% 气声，900 ms |
| `kPurr` 咕噜 | 低沉的"咕噜噜" | 满足、agent 清洁 | 55 Hz 正弦 × 24 Hz 脉动，1.2 s |
| `kChew` 咀嚼 | 三下轻响 | 喂食（人按或 agent 喂） | 每 200 ms 一段 90 ms 滤波噪声，共 600 ms |
| `kSigh` 叹气 | 泄气的"唉" | 受挫、被大声吓到、长按失败 | 420 → 220 Hz，700 ms |

**第七种声音是采样**：夜间床声不是合成的，是一段**真实猫呼噜**（公有领域录音，
9.66 s，309 KB 内嵌）。理由见 §16：合成噪声听上去是嘶声，没有呼噜那种低频脉动。
它单独走一条路径，不占合成器的预算。

**共同规则**：

- 时长 0.3–1.2 s，**不循环、不排队堆叠**：新音效直接顶掉旧的
- **呼噜不只在夜里**：她白天睡着（打盹）也放同一段呼噜床声，音量提到 0.62（原 0.42），
  因为用户觉得打呼太轻
- 包络统一「快起慢收」，避免咔哒声
- 全部乘主音量（0–100，配网页可调），再乘一个 0.6 的固定安全系数
- **夜间不合成任何音效**：夜间只有呼噜床声，以及 agent 明确的 `pet.wake`
- agent 推来的 PCM（`pet.say`）与合成音走同一个混音器，PCM 在合成音之上叠加

**已知取舍**：合成音听起来是"电子猫"，不是真猫叫。要真猫叫得采样，而采样就要
Flash 预算和试听返工——V3 范围内不做，记在 §15 排除项里（音效包）。

### 夜间陪伴

A 的时段模式，也是原方案 D 的全部内容。到点进入，不需要用户操作。

**进入**：作息时段到达（依赖时间源），或长按 BOOT 进菜单手动打开。

**表现**：
- 屏幕亮度降到微光档，表情切到"睡姿"帧，只保留极慢的呼吸起伏
- 呼吸节律音（4–6 次/分的引导节奏），可选白噪音
- 打呼、翻身、偶尔咂嘴——用极低频的随机行为保持"活着"的存在感

**白噪音不占 Flash**：用算法生成（滤波噪声），几十行代码，不用存音频文件。

**禁止项**：夜间不主动行为、不主动搭话。**agent 在夜间一律禁言**——`pet.say` 也在拒绝名单里，
只有 `pet.status`、`pet.ping`、`pet.wake`、`pet.night` 还会应答。半夜被提示音吵醒的代价，
比"漏看一次任务完成"高得多。

**退出**：作息时段结束、轻触按键、或 agent 显式 `pet.wake`，并给出起床表情。

### 昼夜

需要绝对时间；时间源见 §13 未决项。拿不到绝对时间时退化为"仅运行时长"，
昼夜玩法整体关闭，其余不受影响。

## 11. 配网与参数

WiFi 在本设计中**只是配网射频**，不是联网能力。

- **触发**：长按 BOOT 3 s（短按/双击留给养成交互）
- **形态**：SoftAP + HTTP 配置页，带强制门户（见 §16）
- **落盘**：NVS，掉电保留

| 参数 | 说明 |
| --- | --- |
| `name` | 宠物名字（用于唤醒词与界面） |
| `volume` / `brightness` | 音量、屏幕亮度 |
| `led` | 灯的亮度 0–100，**默认 0（关）**；乘在情绪配色上，NVS 保存 |
| `wake_phrase` | 唤醒词，拼音注册（默认 `ni hao xiao mi`） |
| `wake_sensitivity` | 唤醒词灵敏度：低 / 中 / 高（对应 MultiNet 阈值） |
| `sleep_window` | 作息时段（依赖时间源） |
| `personality` | 行为权重档位：黏人 / 冷淡 / 活泼 |
| `difficulty` | 数值衰减速率：轻松 / 正常 / 硬核 |
| `clock` | 手动对时（无网络时的时间源之一） |

不做 WiFi STA 联网。配网页里不需要填 SSID 密码。

### 热点的生命周期

WiFi 射频是整机最耗电的部件，所以热点是**短命**的，从打开那一秒就在倒数：

| 事件 | 计时 |
| --- | --- |
| 打开热点 | 倒计时 180 s |
| 手机**连上**（拿到 IP） | 重置回 180 s |
| 每次打开页面 / 提交表单 | 重置回 180 s |
| 保存成功 | **1.5 s 后**关（留时间把响应发出去） |
| 180 s 没有任何请求 | 关 |

关闭时调 `esp_wifi_stop()`，射频彻底停，**不留 SSID、不扫描、不联网**；
WiFi 驱动本身保留初始化状态（之前 deinit + 重新初始化会 panic 重启，见 §16 的教训）。

关掉之后她回到普通待机：屏、麦克风、喇叭，没有射频。

> 配网期间的功耗没有实测（§13 待实测项）。设计上的原则是**不让它常开**：
> 3 分钟硬上限，加上"保存即关"，正常人配完网射频只会亮几十秒。

## 15. 明确排除

以下内容本设计不包含，未来若要做需单独提案：

- 任何形式的云端 LLM 推理
- 语音转文字、语义理解
- 联网内容（天气、新闻、时间服务）
- 触摸屏（硬件不支持）
- 摇晃交互（无 IMU）
- 养死机制
- 电量显示、低电提醒、充电符号（本板没有电池，也没有检测引脚）
- 声源方向判断（只有一个麦克风）；因此也**没有"眼神跟随声音"**：`pet.look` 是给
  agent 和离线行为用的定向平移，不是跟随声源的注视
- 可替换的音效包、真猫叫采样（现有声音是合成的"电子猫"，见 §10 声音）
- **长按菜单**（配网 / 夜间 / 静音 / 音量三档）：四个选项都有更短的替代路径 ——
  配网就是长按本身、夜间靠作息或 `pet.night`、音量用配网页连续调；
  而菜单要在 128×128 上画界面并做单击切换/长按确认/超时的状态机，代价与收益不成比例
- **新增主动事件**（`pet.hungry` / `pet.woke` / `pet.disturbed`）：设备已经在串口写事件行，
  但 host 侧是"一问一答"的读取方式，MCP 客户端也没有通知通道，**没有消费者**；
  agent 直接读 `pet.status` 更快。要恢复必须先设计事件流，那是一个独立课题

代码位置（严格按 §5 分层，`boards/` 下只剩接线）：

开关：`CONFIG_KITTY_PET_MODE`（本板默认 y）。打开后 `main.cc` 不创建 `Application`，
不连 WiFi、不起协议、不做激活 —— 设备就是一台离线宠物。

与设计的偏差 / 需要知道的事实：

1. **素材的九行是动作，不是情绪脸。** 原 spritesheet 是同一个身体的转身与动作循环
   （待机、转身、跑、挥手、跳、蔫、张望、端详）。所以"开心/生气/困"不是换一张脸，
   而是换一组动作 + 速度 + 灯色。说明书 §6 已按事实改写。
2. **眨眼用缩放做。** 素材没有闭眼帧，眨眼是把脸垂直压到约 90% 保持 120 ms。
   看上去是"眯一下"，不是真正的眼皮。
3. **插电态用 `usb_serial_jtag_is_connected()` 判定。** 这块板没有 VBUS 检测脚，
   只能看 USB 主机在不在。插充电宝时这会判成"没插"，属于已知不精确。
4. **POWER 键不可用**（2026-11-06 真机确认：按一下断电、再按一下上电，是电源锁存开关）。
   所以清洁/陪玩/夜间模式现在都没有入口，`pet_core` 里的 `Clean()`/`Play()` 已经可用，
   只等 §8 的单键菜单接上。
5. **配网页没有。** 长按 BOOT 现在只播一个"端详"动作作为反馈，不改任何参数。
6. **没有音效。** V0 不需要，`AudioService` 也没启动 —— 整机更省电。
7. **衰减速率是估的。** 数值都是真机试玩才能定的，见 §13 未决项 6。

硬件验证（2026-11-05，实测串口日志）：

- 上电 458 ms 内加载 57 帧（PSRAM），创建 128×88 的动画对象
- 数值从 NVS 恢复；60 s 心跳日志正常；连续 75 s 无复位、无看门狗
- 插着 USB 时自动进入 `docked`，心跳里能看到模式

**尚未验证**（需要人动手）：

- 画面观感（呼吸幅度、眨眼的观感、灯色）
- BOOT 短按 / 双击 / 长按的实际手势判定（`iot_button` 的窗口参数没调过）
- 拔掉 USB 后是否稳定回到 `autonomous`

### V1 · 可被接管（已实现）

`main/pet/agent_link.cc` 是第二个大脑：USB 串口上的一行一条 JSON-RPC 2.0。

| 项 | 实现 |
| --- | --- |
| 传输 | USB-Serial/JTAG，和日志共用同一个口；不是 JSON 的行一律忽略 |
| `pet.hello` | 返回名字、固件版本、能力表、完整状态；同时进入 `remote` |
| 心跳 | 3 秒没有一行 JSON 就退出 `remote`，模式交还给「插没插 USB」的判断 |
| 原语 | `pet.face` `pet.look` `pet.attention` `pet.status` `pet.feed` `pet.clean` `pet.play` `pet.task` `pet.sleep` `pet.wake` `pet.ping` |
| 事件 | `pet.poke`（被摸）、`pet.called`（叫名字被听见）、`pet.state_changed`（数值/情绪/模式变了）、`pet.tired`（精力 < 15） |
| 咬合 | `pet.task result=done` → 精力 −5、亲密度 +2；`result=error` → 精力 −8、亲密度 −1 |
| 脚本 | `scripts/pet_agent.py` 假扮 host，把上面每一条都跑一遍 |

与设计的偏差：

1. **`pet.say` 已实现**（`agent_link.cc` 收 base64 PCM 分块 → `PetAudio::PlayPcm()`）。
   host 每块最多 12 KB base64（约 0.3 s），标 `last` 后整段入队播放。
   另有调试开关 `test`：不发声，直接把音频喂给命令模型，用来闭环验证识别链路。
2. **`pet.look` 是整脸平移**，不是眼珠转动 —— 眼睛在帧里，切不出来。±8 px。
3. **代劳上限已实现**：`kAgentCareCap = 85`，agent 代劳每次只补一半（`Feed` +12 对人工 +25），
   且补到 85 就补不动，只有人能补满。
4. **独占 / 抢占**没做：谁的 `pet.hello` 最后到谁说了算，不区分连接。
5. **控制台从 UART0 挪到了 USB-Serial/JTAG。** 之前 USB 只是第二控制台，
   驱动没装、RX 的 64 字节 FIFO 没人取，host 一写就卡住。现在 USB 是唯一控制台，
   固件在启动时就把驱动装好，`read()` 才有东西。代价是日志和 JSON 混在一个流里。

硬件验证（2026-11-05，实测）：

```
-> {"jsonrpc":"2.0","id":1,"method":"pet.hello","params":{}}
<- {"jsonrpc":"2.0","id":1,"result":{"ok":true,"name":"Kitty","firmware":"kitty-pet 0.2.0",
    "capabilities":[...],"status":{"hunger":94,"energy":75,...,"mode":"remote"}}}
<- {"jsonrpc":"2.0","method":"pet.state_changed","params":{...}}
-> {"jsonrpc":"2.0","id":2,"method":"pet.task","params":{"result":"done"}}
<- {"jsonrpc":"2.0","id":2,"result":{"energy":70,"affection":37,...}}   # 精力 75 -> 70
-> 之后不再发任何东西
<- I (3520) PetLink: Back on her own: heartbeat timeout
<- I (3520) PetCore: Mode remote -> docked
```

未知方法返回 -32601；`pet.sleep`/`pet.wake` 让 `mood` 在 `asleep` / `content` 之间切换，
都被 `pet.state_changed` 报出来了。`pet.say` 是后加的，见上面第 1 条。

4. **唤醒灵敏度这一项留空**：没有唤醒词，填了也没用。

### V2 后续 · 耳朵与命令词

`main/pet/pet_ears.cc` 已经给麦克风开了一条通路：一个 32 ms 一帧的采集任务，
算 RMS、维护一个缓慢的房间噪声基线，超过阈值就"吓一跳"。

```
I (341) PetEars: No command model: she will only notice loud noises
I (361) PetEars: Sound: rms 21663 (floor 727, trigger 4200)
I (371) PetEars: Loud noise: rms 21663 (floor 727)
```

唤醒词（MultiNet 中文命令词）做到了哪一步，为什么停在这里：

1. **模型放得下。** 打开 `CONFIG_SR_MN_CN_MULTINET7_QUANT=y` 后固件从 3.15 MB 长到 3.34 MB，
   离 4 MB 分区还很远。
2. **但模型不在固件里，而在资源包里。** 这一版 esp-sr（2.4.7）的 `esp_mn_handle_from_name()`
   会去 `/srmodel/mn7_cn/mn7_index` 找文件，找不到就**不返回**（板子直接卡死在那里，
   日志停在 `Please check if there are target files in /srmodel/mn7_cn/mn7_index`）。
3. **资源包里没有它。** 当前的 `generated_assets.bin` 只打了 WakeNet 的 `srmodels.bin`
   （里面有 `wn9`，没有 `mn7`）。要真的认名字，需要：
   - 让 `scripts/build_default_assets.py` 把 MultiNet 模型一起打进 srmodels；
   - 运行期挂载 assets 分区、`srmodel_load()` 出 model list、再 `esp_srmodel_filter()`；
   - 这条链要动资源生成脚本，属于独立的一块工作。

后来这条链已经接通了（见下面"唤醒词"一节），剩下的只是"识别率"问题。

## 唤醒词 · 现在的样子

| 件 | 状态 |
| --- | --- |
| 模型 | `CONFIG_SR_MN_CN_MULTINET7_QUANT=y`，`config.json` 里 `"wake_word": "custom"` |
| 资源 | 构建时把 `mn7_cn` + `fst` 打进 `srmodels.bin`（资源包 1.2 MB → 3.6 MB，8 MB 分区够用） |
| 加载 | `Ears::Start()` 读 `index.json` → `srmodel_load()` → `esp_srmodel_filter("mn","cn")` |
| 命令词 | NVS `wake_phrase`（默认 `ni hao xiao mi`），`esp_mn_commands_alloc/add/update` |
| 采音 | 16 kHz 单声道，32 ms 一帧；麦克风增益 38 dB，送模型前再放大 3 倍 |
| 回调 | 命中 → 抬头、两声雀跃、`pet.called` 事件推给 host |

`scripts/build.py` 加了一个 `custom` 唤醒词档位，并且允许 variant 在 `config.json` 里用
`"wake_word"` 指定自己的唤醒词 —— 否则这个组合只能靠手敲 menuconfig 复现。

还有两件事要说清楚：

1. **识别率没在真人身上验证过。** 我手上的唯一声源是笔记本 SPDIF（没接音箱，实测无声）
   和板子自己的小喇叭。用 TTS 把"你好小咪"推给她、从自己的喇叭放出来再自己听，
   能量是够的（rms 1560），但模型没命中 —— 这不代表真人说话也不行，
   只是我这边没法证明。**需要人对着板子说一句。**
2. **`pet.say` 顺手做出来了**：一行一条 base64 PCM16，单条上限 12 KB（约 0.3 秒），
   host 分片推。这也算把 V1 里"agent 推音频让她说话"那条补上了。

### 唤醒词 · 调参记录（第二轮）

1. **模型只加载一次。** `Ears::Start()` 原来每次退出夜间都会重新 `srmodel_load()`，
   等于把权重再拷一份进 PSRAM；夜里起来一次就把堆吃干，紧接着
   `Item psram alloc failed` 然后 panic。现在 bundle 与 model 实例都是懒加载、只建一次。
2. **PSRAM 预算。** 这块板 8 MB，原本 LVGL 拿走 2.5 MB 池 + 2 MB 图片缓存，
   加上 1.28 MB 帧和 ~1 MB 模型，只剩 442 KB。把这两个数做成 Kconfig
   （`LV_PSRAM_POOL_EXTRA_KB` / `LV_IMAGE_CACHE_KB`，默认值保持原样），
   本板设成 1024 / 512，空闲回到约 2.4 MB —— 现在整机有 2.4 MB 余量。
3. **`pet.say` 改成先攒后放。** 分片边收边播会断断续续，模型听断句更不可能命中；
   现在收到 `last` 才一次性交给播放。缓冲 4 s（可退到 2 s / 1 s）。
4. **`calls` 计数。** 她每"听到名字"就给 NVS 里的计数 +1，`pet.status` 里带出来。
   这样验证不需要有人守在串口前：说一句、过一会儿读 `calls` 就知道。
5. **离线自测。** `pet.say` 支持 `{"test": true}`：不播放，直接把这段 PCM 喂给命令模型，
   返回识别结果。用它把"模型认不认"和"房间传不传得进来"分开了 ——
   结果是**连数字音频都不认**，所以问题不在麦克风，在模型与合成语音的匹配上。

### 唤醒词 · 第三轮：模型是好的

关键实验：用 `edge-tts`（神经语音，zh-CN-XiaoxiaoNeural）合成"你好小咪"，
把 PCM 直接喂给命令模型（`pet.say {"test": true}`）：

```
I (9951) PetEars: Offline test heard:  ni hao xiao mi (prob 0.28)
```

**模型、命令图、pinyin 全部是对的。** 之前一直不响，是 Windows 自带的
Microsoft Huihui（2010 年代的拼接式语音）压根不在模型的训练分布里。

所以现在的状态是：

| 环节 | 结论 |
| --- | --- |
| 命令词图 | ✅ 运行期替换有效，`ni hao xiao mi` 生效 |
| 模型 | ✅ 能识别自然语音（概率 0.28，阈值 0.12） |
| 数字通路 | ✅ 喂 PCM 就能命中 |
| 声学通路 | ❓ 房间里的声音进不了麦克风（rms 只有几百，模型需要几千） |

声学这一环有三条待办：
1. 真人对着板子说（音量远大于我这边 0.85 寸喇叭重放）；
2. 或者把蓝牙音箱的音量开到能听清、靠近板子；
3. 代码侧已经做了自适应归一化（每 32 ms 把信号拉到 rms 3500，增益上限 8 倍），
   阈值 0.12 —— 这两条都是为"小声也能唤醒"准备的。

`pet.record`（把麦克风数据回传）做了一半就去掉了：I2S 只有一个消费者，
录音任务和听音任务抢同一个 codec，把 `pet_link` 任务拖进了看门狗。
把这条调试通道再打开前，得先让两者互斥。

### 唤醒词 · 通了

把 1 kHz 音调和 edge-tts 的"你好小咪"通过蓝牙音箱放到房间里，她的麦克风收到
rms 1500–2200（安静时 ~330），命令模型连中三次：

```
I (2842) PetEars: Heard her name:  ni hao xiao mi (prob 0.07)
I (5682) PetEars: Heard her name:  ni hao xiao mi (prob 0.12)
I (8502) PetEars: Heard her name:  ni hao xiao mi (prob 0.07)
```

`pet.status` 的 `calls` 从 0 变成 3，说明计数也落盘了。随后 **120 秒静音零误触**。

最终参数：

| 项 | 值 | 说明 |
| --- | --- | --- |
| 麦克风增益 | 42 dB（ES8311 上限附近） | 板载麦克风很小 |
| 送模型前归一化 | 目标 rms 6000，增益上限 12× | 每 32 ms 调整一次 |
| 检测阈值 | 0.05 | 命中概率只有 0.05–0.12，因为房间里信号偏弱 |
| 命令词 | `ni hao xiao mi`（NVS `wake_phrase`） | 可在配网页改 |

要紧的是**概率很低**（0.05–0.12），说明信噪比贴着实底线。真人靠近说话会高得多，
但如果房间很吵、或者离得远，就可能叫不醒 —— 这是硬件（单个小麦克风、无 AGC）
决定的，不是调参能解决的。要更稳只能上 AFE + AGC，或者换麦克风。

顺带修的两处：
- 归一化原来按每块 32 ms 独立算，静音段会把底噪放大 12 倍；现在增益有上下限且
  低概率同时压住了误触。
- 录音回传（`pet.record` / `pet.mic`）两次尝试都把设备搞进看门狗或重启，
  已经从固件移除；耳朵内部的 5 秒环形缓冲留着，等音频通路真正能互斥了再开。

### 收尾：灵敏度与两处崩溃

手册里最后两项能做出来的缺口：

- **唤醒灵敏度**（§14 参数表）：低/中/高 → 检测阈值 0.08 / 0.05 / 0.03，
  配网页可改，NVS 键 `wake_sens`。实测 0.03 在安静房间连跑 60 秒零误触。
- **灯快速闪烁**（§10）：agent 接管时 4 Hz 明灭，交还后回到呼吸。

过程中踩到两个真 bug，都不是"逻辑写错"，而是"边界":

1. **NVS 键名超长**：`wake_sensitivity` 有 16 个字符，NVS 上限 15，于是
   `nvs_set_i32` 返回 `ESP_ERR_NVS_KEY_TOO_LONG`，而 `Settings::SetInt` 用
   `ESP_ERROR_CHECK` 包着 —— 保存配网页直接 abort 重启。改成 `wake_sens`。
   这类错误只在写的时候炸，读的时候静默返回默认值，所以更难发现。
2. **`pdMS_TO_TICKS(5)` 在这个工程里等于 0**：`CONFIG_FREERTOS_HZ=100`，
   5 ms 换算成 tick 是 0，`vTaskDelay(0)` 不会让出 CPU 给空闲任务，
   于是 `pet_link` 任务把 IDLE1 饿死 → 看门狗复位。改成 `vTaskDelay(1)`。

两个 bug 都是"看起来正常的代码在特定配置下不成立"，值得记在文档里。

### 用 agent 真机驱动（petctl）

之前验证协议用的都是 `scripts/pet_agent.py`：一个把每条原语按顺序打一遍的脚本。
那是"脚本假扮 agent"，不是 agent 在决策。补了一个 `scripts/petctl.py`：

```
python scripts/petctl.py status
python scripts/petctl.py clean
python scripts/petctl.py task result=done
python scripts/petctl.py say --wav hello.wav
```

一次调用一条 JSON-RPC，开串口**之前**就把 DTR/RTS 置低（否则开串口会复位板子），
所以任意 agent 框架、任意 shell 都能用。大块数据要分片写（128 字节 / 4 ms），
否则 1 KB 的接收环会溢出、整行丢失。

用这个桥实际跑了一轮，agent 侧按状态做决定：

| 命令 | 结果 |
| --- | --- |
| `status` | `clean 69`，其余满值 |
| `clean` | 69 → 87，`mood` 变 happy |
| `task result=done` | energy 100 → 95、affection +2 |
| `task result=error` | energy 95 → 87、affection −1 |
| `face emotion=happy` | ok |
| `say --wav` | 28 片推流，她真的说出来了 |
| `night on` | 之后 `face` 返回 −32001，`status` 仍可读 |
| `wake` | 回到白天 |

这一轮抓出两个**只有真机驱动才会暴露**的偏差，都已修：

1. **夜间没真睡着。** `ForceSleep()` 之后 `Tick()` 看到精力 ≥ 唤醒阈值（85）当场又把她
   叫醒，`status` 里 `sleeping` 一直是 false。现在夜间不自动醒（`if (energy_ >= kWakeAt && !night_)`）。
2. **代劳上限是"进门检查"不是"封顶"。** 文档写"补到 85 就补不动"，实际是从 69 一次补到
   87 —— 因为判断在加之前、且只比较起始值。现在补完再钳到 85。

### 她说话到底清不清楚

用户听到她说话像 "huan cai hao han geng"。用她的麦克风量了一下自己的喇叭：

```
放 1 kHz 正弦 → 麦克风测回 999.5 Hz（rms 2564，峰值 5845）
```

**采样率是准的**，通路没有变速变调。真正的原因是音源：Windows 自带的
Microsoft Huihui 是拼接式老语音，经 0.85 寸小喇叭糊成一片；换成 edge-tts 的神经语音，
同一个通路放出来用户当场听清了"你好小咪"。

顺带一个自证：让她自己说"你好小咪"时，她自己的麦克风把这句话认了出来
（`calls` 计数 +1）—— 声学回路和命令模型同时在正常工作。

### 夜间床声：从合成噪声换成真的猫呼噜

第一版是"低通滤波噪声 + 12 秒呼吸包络"，用户听感是"太吵" —— 合成噪声缺少
呼噜那种低频脉动，听上去就是嘶声。

换成了 Wikimedia Commons 上的 [Purring cat.oga](https://commons.wikimedia.org/wiki/File:Purring_cat.oga)
（Mysid 2007 年录制，作者声明公有领域）。处理链在 `scripts/make_purr.py`：

1. 整段保留（9.66 s），不剪 —— 剪短后循环点更容易听出来；
2. 22.05 kHz → 16 kHz（板子的输出采样率）；
3. 两端 120 ms 交叉淡化，循环接缝听不见；
4. 1.2 kHz 窗函数低通，去掉录音里的嘶声（呼噜的能量 85% 在 1 kHz 以下）；
5. 归一化到 0.85 峰值，固件里再乘 0.42 × 主音量，并叠加 12 秒呼吸起伏。

固件侧：`purr.pcm` 走 `EMBED_FILES`（309 KB，应用分区从 3.36 MB 长到 3.67 MB，
4 MB 分区仍有余量），`PetAudio::Fill()` 在夜间循环读它，不再生成噪声。
用户实测"刚好"，参数定在此处。

注意：夜间模式会关闭麦克风（省电），所以这段床声**没法用她自己的麦克风自测**，
只能靠人耳验收 —— 这是当前设计的取舍。

### 画面镜像

屏上的 Kitty 是反的（设备要挡在一块反射面后面看，正面看到的是镜像），所以
`main/pet/assets/pet_frames.bin` 里的 57 帧已经**左右翻转**过：

- 翻转在帧数据上做，不动面板的 `mirror_x` / `mirror_y` —— 那两个参数作用于整个 GRAM，
  改它们会连带影响 LVGL 的所有图层；
- `scripts/gen_pet_frames.py` 里 `MIRROR_X = True` 保证以后重新生成帧不会把这个镜像丢掉；
- 实机确认：Kitty 的朝向由面向左变成面向右，用户验收通过。

**LVGL 画的东西也要跟着变换。** 片上唯一会显示文字的场合是配网小黑板（SSID + 地址）。
它现在先画到离屏 canvas，再把像素做和帧一样的变换（逆时针 90° + 水平镜像），最后以
`lv_image` 贴到屏幕上 —— 直接放 `lv_label` 的话，字会是歪的而且是反的。

canvas 用 **ARGB8888**、背景全透明：字之间的像素带 alpha=0，所以脸会透过来，
不再是一块黑底盖住她；白字底下垫了一层 1 px 黑阴影，保证在浅色的 Kitty 脸上也读得清。
变换映射：`dst_x = H-1-y`、`dst_y = W-1-x`，和 `gen_pet_frames.py` 的 PIL 处理（rotate 90 + FLIP_LEFT_RIGHT）逐像素等价。

### 接入 DSH（MCP）

除了 `petctl.py`（一次调用一条请求）和 `pet_agent.py`（脚本跑全部原语），还有第三条路：
把设备协议包成 **MCP server**，让 agent 框架原生调用。

- `scripts/pet_mcp.py`：stdio JSON-RPC，实现 `initialize` / `tools/list` / `tools/call`，
  17 个工具一一对应 `pet.*` 原语（含为 agent 补的 `pet.config`）；
- `dsh/kitty-mcp/`：只有配置的 DSH bundle，把上面的 server 注册成
  `@deepseek-ai/dsh-mcp-client` 的一行配置（`transport: stdio`、`command`、`args`、`env`）。

关键设计：**连接是持久的，并且带心跳。** MCP 的一次 `tools/call` 只是打开串口、发一条、
关掉；那样每次调用之间都会超过 3 秒，她会掉回 `autonomous` 并把 agent 设的表情覆盖掉。
所以 server 首次调用时建立连接、发 `pet.hello` 接管，然后后台每秒 `pet.ping`，
直到进程退出才关端口。

实测（通过 DSH 原生工具调用，不经过 shell）：

```
pet_status  -> mode: remote           # hello + 心跳生效，持续接管
pet_time    -> minute_of_day 1317      # agent 负责对时
pet_task done -> energy 96 -> 91       # 咬合正确
pet_face happy -> ok                   # 表情不再被本地循环覆盖
pet_night on  -> night: true
pet_face angry -> -32001               # 夜间拒绝，错误穿到工具层
pet_wake      -> ok
```

### 强制门户（手机自动弹配置页）

只有 HTTP 服务时，手机连上热点不会弹任何东西 —— 系统的探测请求要么失败（没有 DNS），
要么拿到一个 200（我们自己的页面），两种都被判定为"这个网络正常，不需要登录"。

补了两件事：

1. **DNS 兜底**：一个 UDP 53 的小服务，任何 A 查询都答 `192.168.4.1`；
2. **通配 302**：`httpd` 注册 `/*`，把不是自己页面的请求全部 302 到 `http://192.168.4.1/`。

坑：`httpd_config_t` 默认的 `uri_match_fn` 是精确匹配，`/*` 注册了也永远不会命中
（日志里只会看到 `URI '/hotspot-detect.html' not found`）。必须显式设成
`httpd_uri_match_wildcard`。

实测三种系统的探测路径都返回 302：

```
Host: captive.apple.com          GET /hotspot-detect.html  -> 302 http://192.168.4.1/
Host: connectivitycheck.gstatic.com GET /generate_204     -> 302
Host: www.msftconnecttest.com    GET /connecttest.txt     -> 302
```

### 灯的词汇表

灯原来只有两种模式（呼吸、4 Hz 闪）和一个颜色，情绪基本传不出去。现在拆成两个正交通道：

- **颜色 = 情绪**，仍由 `pet_expression.cc` 的 `Look` 给出；
- **节奏 = 状态**，`LedPattern`：3 s 呼吸 / 6 s 深呼吸 / 双闪（饿）/ 4 Hz 闪（被接管）/
  常亮（睡着）。

`Action::Flash()` 提供短促的颜色爆发（叫名字白、任务完成绿、失败红），
盖过情绪色后自己回去。

三个踩过的坑，都写进代码注释了：

1. **颜色必须饱和。** 平静色曾用 `(255,208,160)`，满亮度就是一颗白灯；
2. **灯要默认关。** 桌上的一颗高亮 LED 默认亮着只会碍事，`led` 默认 0，
   旧固件存过 100 的用 `led_rev` 做一次性迁移清零；
3. **灯不能跟着脸的控制权走。** 颜色原本在 `ApplyLook()` 里设置，而 agent 接管时会跳过它，
   于是灯冻结在上一刻的颜色（删掉脏检查后变成冻结在黑色，看起来就是"默认不亮"）。
   现在每个 tick 由身体状态独立驱动：agent 借脸，不借整个身体。

`pet.status` 里带 `led: {r,g,b,level}`，可以在没有摄像头的情况下确认灯的真实输出。

### 动画校对（对着帧看出来的三处）

把 `pet_frames.bin` 解出来、逐组渲染成图看了一遍（9 组全部正常：红蝴蝶结、蓝背带裤、无串色无撕裂）。
看不出问题的地方没问题，看出来的三处都是"分组用错"或"画蛇添足"：

1. **打哈欠用了敲电脑那组**（`kReview`，屏幕里是她在用笔记本电脑）。哈欠应该用 `kFail` ——
   那组是闭眼低头的 8 帧，读起来就是困。伸懒腰同理，改用 `kJump`（举双手 + 身体上抬）。
2. **东张西望用了摇摆那组**（`kWait`）。`kRun` 才是真正左右转头的那组。
3. **合成眨眼是多余的**。美术自己在 idle / wait / run 里就眨眼（有闭眼帧），
   代码又每几秒把整张图纵向压到 90%，读起来是"跳一下"而不是眨眼。合成眨眼整个删掉，
   只留呼吸的 ±2 px 平移。
4. 顺带一个**看不出来但会静默失效**的：单击第四种反应原本用 `kIdle`，而 `kIdle` 通常就是
   当前正在播的那一组，`Play()` 对同组同速会直接 return —— 按下去屏幕毫无变化。改用 `kRun`。

教训：**动画素材要先渲染出来看一遍再写映射**。这三处都不是崩溃，是"看起来不对但没人报错"。

### 屏幕版式：脸 + 侧边 HUD

屏是 128×128，帧是 128×88，所以正方形面板上天然有 40 px 的富余。这些像素现在用来做状态栏：

- 脸贴到面板**顶部**（`LV_ALIGN_TOP_MID`），占 88 行；
- 底部 40 行是 HUD 带，经分光镜旋转后落在**观者的左侧竖条**（40 px 宽 × 128 px 高）。

HUD 内容是 40×128 的离屏 canvas，画完再做和帧、小黑板完全相同的变换
（`dst_x = 127 - vy`、`dst_y = 39 - vx`）贴到面板底部。图标是像素画，因为
14–18 px 的尺寸下没有可用的图标字体：

| 图标 | 含义 | 数据来源 |
| --- | --- | --- |
| 红心 | 亲密度，**从底部往上填充** | `affection` |
| 碗 | 饱食，同上 | `hunger` |
| 插头 | USB 主机在另一头（docked / remote） | `status.mode` |
| 电池 | **只有轮廓**：本板没有电池检测，这是"没有读数"而不是"空电" | 无 |
| WiFi 扇面 | 只在配网热点开着时显示，关闭时整个图标消失 | `Gateway::active()` |

只在数值变化时重绘（`SetHud` 里比较缓存），因为整条 HUD 是逐像素写 canvas，
1 Hz 级别的更新足够，没必要每个 tick 都做。

坐标推导（viewer → panel）：`panel_x = 127 - vy`、`panel_y = 127 - vx`。
脸在 viewer 的 `x ∈ [40,128)`，所以 panel 的 `y ∈ [0,88)`；HUD 在 viewer 的
`x ∈ [0,40)`，落在 panel 的 `y ∈ [88,128)`。

### 电池读取（硬件存在，读数待查）

原理图确认：`V_BAT → R24 100K → VBAT_ADC → R26 100K → GND`，C60 0.1µF 并联在下臂，
分压比 1:2；`VBAT_ADC` 接 **GPIO1**（原理图 pin 6）。所以 4.2 V 电池应在引脚上读到 2.1 V。

实现：`main/pet/pet_battery.cc`，ADC1 channel 0、12 dB、曲线拟合校准，每秒最多读一次
（50K 源阻抗 + 0.1µF，采样太密会把读数拖低），`pet.battery` 返回 `{mv, percent, present}`。

**实测结果不成立**：开机后第一次读到 628 mV（≈1.26 V 电池），之后立刻塌到约 135 mV 并稳定，
说明引脚上看不到低阻源——100K/100K 分压的等效内阻只有 50K，不可能被 ADC 拉到 0.13 V。
两种可能：分压中点未连到该脚（R24 未贴/版本差异），或电池座只接了部分电极。
**待用万用表量 VBAT_ADC 节点（GPIO1 对 GND）确认**：应为 2.1 V。

在那之前，HUD 的电池图标按"无读数"显示成暗色空壳，`pet.battery` 返回 `present: false`。
读数一旦成立，图标会自动按 3.3–4.2 V 线性填充。
